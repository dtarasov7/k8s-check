### Как различать обычную проверку и инцидент

Я рекомендую не делать два независимых сборщика. Нужен один pipeline и явный параметр цели анализа:

```bash
kdiag snapshot --purpose check ...
kdiag snapshot --purpose incident --incident-since 2h ...
```

В дальнейшем можно добавить `--purpose auto`, но не делать его первым вариантом: автоматический триггер может не заметить нестандартную проблему и собрать слишком мало данных.

`check` должен:

- показывать активные ошибки и недостатки конфигурации;
- проверять Node, API, workloads, DNS, runtime, storage, сертификаты;
- подавлять завершившиеся единичные события;
- не пытаться объявлять каждое старое сообщение частью инцидента.

`incident` должен:

- принимать `--incident-start`, `--incident-end` или `--incident-since`;
- строить временную шкалу вокруг начала сбоя;
- различать `первопричина`, `следствие`, `сопутствующая проблема`, `не связано`;
- собирать расширенные current/previous logs;
- запрашивать Prometheus range queries за то же окно;
- выдавать ранжированные гипотезы с подтверждениями, противоречиями и недостающими проверками.

Третий режим — `baseline` — должен появиться отдельно. Обычная проверка и утверждённый baseline — разные сущности: случайно успешный запуск нельзя автоматически считать эталоном.

### Главные ограничения

1. Отдельного назначения запуска нет. CLI содержит только общий `snapshot`; `fast-triage/deep-analysis` относятся уже к LLM-пакету, а не к сбору: [cli.py](/home/devuser/k8s-check/src/kdiag/cli.py:24).

2. Корреляция сейчас состоит всего из восьми заранее заданных сочетаний с фиксированным окном 15 минут: [normalize.py](/home/devuser/k8s-check/src/kdiag/normalize.py:116). Scope в основном ограничен одним узлом или Pod: [normalize.py](/home/devuser/k8s-check/src/kdiag/normalize.py:792).

3. Нет причинного графа:

```text
Service → EndpointSlice → Pod → Node → CNI/runtime/kernel
PVC → PV → CSI → Node/storage
API server → etcd/control-plane
```

Поэтому kdiag может обнаружить одновременно `NodeNotReady`, CNI error и рестарты Pod, но не всегда правильно отделит причину от каскадных следствий.

4. Findings сортируются по severity и идентификатору правила, а не по вероятности быть первопричиной: [rules.py](/home/devuser/k8s-check/src/kdiag/rules.py:2413).

5. Prometheus сейчас не даёт исторических метрик. Запрашиваются только `/api/v1/alerts` и `/api/v1/status/runtimeinfo`: [kubernetes.py](/home/devuser/k8s-check/src/kdiag/kubernetes.py:1064). Без `query_range` невозможно увидеть, что первым выросло: API latency, packet drops, memory pressure, etcd latency или число рестартов.

6. Внешний LLM-пакет хорошо минимизирован и проверяется fail-closed, но это псевдонимизация. Редкая комбинация версий, компонентов и топологии потенциально позволяет повторную идентификацию. Поэтому ручная проверка экспорта всё равно обязательна: [README-ru.md](/home/devuser/k8s-check/README-ru.md:199).

7. Каталог правил прямо ограничивает совместимость Kubernetes версиями 1.24–1.31: [rule_catalog.py](/home/devuser/k8s-check/src/kdiag/rule_catalog.py:45). Поддержку «1.24 и всех последующих» пока заявлять нельзя.

8. Поддержка Deckhouse проверена unit/synthetic-тестами, но ещё не подтверждена повторным canary-снимком реального целевого кластера.

### Что следует реализовывать дальше

Приоритетный порядок:

1. `--purpose check|incident` и явное окно инцидента.
2. Статусы findings: `активно`, `завершилось`, `неизвестно`; роли: `возможная причина`, `следствие`, `конфигурационный риск`.
3. Prometheus `query_range` с небольшим фиксированным каталогом диагностических запросов.
4. Топологический причинный граф и ранжирование гипотез.
5. Отдельный утверждаемый baseline и сравнение с ним.
6. Compatibility fixtures для vanilla 1.24/1.31+ и нескольких версий Deckhouse.
7. Только после этого — расширение LLM-пакета временной шкалой и причинным графом.

LLM здесь должна быть последним аналитическим слоем, а не заменой корреляции. Она полезна для неизвестных сообщений и выбора между несколькими гипотезами, но отсутствие Prometheus history, нужных логов или связей между объектами интернет-поиском не компенсируется.

Проверка артефакта `0.9.2`: 129 unit-тестов и `self-test` прошли, rule pack `2026.08.13`, каталог содержит 98 правил. Process-root fallback для `etcdctl`/Cilium, Deckhouse DNS ConfigMap и фильтрация штатных сообщений покрыты synthetic regression-тестами; необходим повторный canary на целевом Deckhouse-кластере.
