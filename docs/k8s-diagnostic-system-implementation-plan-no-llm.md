# Plan

Реализовать без LLM один последовательно наращиваемый диагностический контур для Kubernetes 1.24 и РЕД ОС 7.x: ручной аварийный снимок станет основой периодического baseline, а затем будет дополнен непрерывным Kubernetes WATCH и сбором журналов. Решение и его центральный каталог данных размещаются на одном отдельном управляющем сервере вне диагностируемого кластера; третий сервер или отдельная СУБД не требуются. Prometheus используется только как необязательный источник дополнительных доказательств, поэтому его отказ не нарушает сбор и анализ. План развивает выводы [предпроектного анализа](k8s-diagnostic-system-analysis.md).

## Scope

- In: Python 3.8 с преимущественно стандартной библиотекой; штатные CLI РЕД ОС, Kubernetes и OpenSSH; существующий Ansible 2.13/inventory как опциональный способ discovery, развёртывания и разового запуска; JSON/JSONL, gzip и локальный SQLite; детерминированные правила, evidence-based отчёты и три последовательных режима работы.
- Out: LLM любого типа; автоматическое исправление; обновление Kubernetes; переход на Deckhouse; зависимость от in-cluster Prometheus; неограниченное долговременное хранение всех прикладных Pod logs; замена существующих Prometheus/SIEM/log backend; разработка собственного универсального Kubernetes-клиента, SSH-протокола, YAML-парсера или rule DSL без отдельной необходимости.

## Action items

[ ] Зафиксировать входные данные, эксплуатационные бюджеты и критерии успеха до начала кода.

- Подтверждено: отдельный управляющий сервер имеет SSH-доступ ко всем узлам и доступ к Kubernetes API VIP; масштаб — до 20 Node и 1000 Pod; CNI — Cilium; Pod и host processes kube-proxy отсутствуют; persistent journald включён; Kaspersky — семейство KESL v2; CRI logs ожидаются в стандартных `/var/log/pods`/`/var/log/containers`; прикладные namespace задаются конфигурацией; отдельную Kubernetes identity создать можно, отдельную SSH identity — нельзя; предварительные сроки/RPO/load targets приняты; для каталога данных решения на управляющем сервере первоначально выделено 5 ГБ с возможностью обсуждать расширение; на каждом Node доступно до 5 ГБ свободного места.
- Автоматически инвентаризировать количество и роли узлов, точные `RED OS minor / kernel / container runtime / Cilium / Kaspersky RPM NEVRA`, Cilium `kubeProxyReplacement`, фактические CRI paths/rotation и версии утилит. «Стандартные пути» и KESL v2 до проверки считаются рабочими гипотезами; отсутствие kube-proxy подтверждено наблюдением, но корректность service handling требует отдельной проверки effective Cilium mode.
- Проверить на каждом классе узлов наличие и поведение `python3.8`, `journalctl`, `systemctl`, `ip -j`, `ss`, `findmnt`, `rpm`, runtime CLI и других уже установленных утилит; различия оформить как versioned adapters.
- Инвентаризировать CPU, RAM, отдельную локальную файловую систему, свободный диск и backup центрального сервера, а также выбрать независимый от Kubernetes канал контроля состояния.
- Имеющийся `sudo` сузить для автоматизации до проверяемой privilege model: root service с root-owned кодом/config и единственным writable spool либо dedicated user с ACL/group-доступом и отдельным root oneshot; общий `sudo python3` не использовать. Поскольку отдельная SSH identity недоступна, использовать существующую identity только через pinned `known_hosts`, `BatchMode=yes`, фиксированные remote subcommands, аудит и минимальный `sudoers`; этот residual blast radius зафиксировать в threat model.
- Имеющийся super-admin использовать только вручную для bootstrap/создания разрешённой отдельной диагностической identity. Постоянный snapshot/timer/WATCH получает отдельные credentials и минимальный read-only RBAC без `secrets`, `exec`, `portforward` и write; `pods/log` разрешается только системному профилю и настроенным namespace. Хранить super-admin kubeconfig на collector нельзя.
- Определить нейтральный `transport.json`. Для простого inventory его можно формировать фильтрацией `ansible-inventory`; сложные ProxyJump/vault/plugin cases должны разрешаться в заранее проверенные OpenSSH aliases, а не переноситься в shell arguments. Выбрать и реализовать только один orchestration adapter первого этапа — Ansible CLI либо системный OpenSSH.
- До варианта 3 провести feasibility-spike на фактических `kubectl`/API/auth: paginated LIST, raw WATCH framing, `BOOKMARK`/`ERROR`, disconnect, `410 Gone`, ограниченный `timeoutSeconds` и перечитывание credentials. Результатом является выбранный transport или ранний NO-GO, а не два параллельных клиента.
- Создать feature matrix, sizing sheet и формальный pass/fail-протокол gates: точные числа запусков/циклов, длительность soak, допустимые false findings, resource thresholds и обязательные fault cases. Без этих значений нельзя обещать непрерывный сбор всех Pod logs или пригодность SQLite на полном потоке.

Параметры ёмкости означают следующее; значения в последнем столбце — стартовая гипотеза для пилота, а не production SLO:

| Параметр | Смысл | Предварительное значение |
|---|---|---|
| Incident window | История относительно момента инцидента, попадающая в evidence; это не срок хранения | snapshot: `T-24h` до конца сбора плюс previous boot при наличии; continuous: возможность закрепить `T-24h ... T+4h`, с source byte limits и явным coverage/gap |
| Retention | Сколько уже принятые данные хранятся до контролируемого удаления | continuous raw — 7 суток; baseline raw — 30 суток; approved baseline/facts/findings — 180 суток; вручную pinned incident bundle — 90 суток |
| RPO | Максимальная безвозвратная потеря уже возникших evidence после отказа; не равно времени автономности | normal ingest — не более 5 минут при доступных SSH/central; node spool должен выдержать 24 часа их недоступности; central-disaster RPO определяется частотой отдельного backup |
| Disk budget | Quota данных плюс обязательный свободный резерв | управляющий сервер: общий стартовый лимит 5 ГБ, из них operational data не более 4 ГБ и минимум 1 ГБ для staging/recovery; Node: не более 1 ГБ spool при сохранении не менее 4 ГБ исходного свободного места; окончательная потребность рассчитывается по peak rate × retention/outage target |
| Node load | Добавочная нагрузка collector на один узел | provisional continuous p95: до 5% одного CPU core и 128 MiB RSS, hard limits 10% core/256 MiB; IO — без измеримого роста iowait/PSI; snapshot сначала по одной тяжёлой команде и не более чем на двух узлах параллельно |

- До production-варианта 3 провести семидневный sizing pilot: измерять bytes/records по source в 1/5/60-minute buckets, compression ratio, top talkers, CPU/RSS/IO/network, API load, backlog/drops и размеры snapshot. Для самого пилота достаточно счётчиков и короткой rolling retention в пределах 5 ГБ. После pilot пересчитать retention/spool/disk по фактическому daily maximum и burst с safety factor; повторить расчёт после первого учебного или реального инцидента.
- На управляющем сервере установить hard quota 5 ГБ, operational high-watermark 4 ГБ и сохранить 1 ГБ для `.part`, SQLite recovery и формирования отчёта. При high-watermark прекратить новые opt-in application logs, затем сокращать только rolling low-priority retention по утверждённой политике; pinned incidents, approved baseline и critical data тихо не удалять. Если защищённые данные сами достигают лимита, остановить новый low-priority ingest и сформировать запрос на расширение.
- На каждом Node первоначально ограничить spool одним ГБ и прекращать low-priority запись раньше, если свободное место приближается к 4 ГБ или появляется DiskPressure. Оставшиеся 4 ГБ не считаются ресурсом collector. Если 1 ГБ не обеспечивает 24 часа critical sources, сократить outage target/sources либо согласовать увеличение диска; 24-часовую автономность до sizing не гарантировать.
- Учесть recovery backlog: после длительного central outage суммарный spool двадцати Node может быть значительно больше 5 ГБ. Production GO для варианта 3 возможен только если измерения докажут, что rolling deletion и 5 ГБ сохраняют утверждённые critical retention/RPO, либо после согласованного расширения каталога данных.

Не добавлять `kubernetes`, `requests`, `PyYAML`, `systemd-python`, `psutil`, `watchdog`, ORM или отдельный шаблонизатор без измеренной необходимости и доступного offline-пакета.
- Хранить конфигурацию, схемы и metadata правил в строгом versioned JSON. Условия первых правил реализовать небольшими Python-функциями; не строить универсальный DSL.
- Выполнять команды только из статического registry как массивы `argv`, без `shell=True`. Command runner использует `Popen(start_new_session=True)`, одновременно и ограниченно читает stdout/stderr, убивает всю process group по timeout/limit и всегда вызывает `wait()`; запускается с фиксированными `PATH`/locale, очищенным proxy/environment и не журналирует чувствительные argv/environment.
- Ввести единый envelope: `schema_version`, `collection_id`, `cluster_id`, `source_id`, `node_uid`, `boot_id`, UTC timestamps, `status`, `sensitivity`, `truncated`, `payload_hash` и `evidence_ref`.
- Разделить raw evidence, нормализованные facts, findings и отчёты. Raw хранить в ограниченных gzip JSON/JSONL-сегментах, SQLite использовать только для индекса, cursors, baseline и findings; SQLite должен иметь одного writer и находиться на локальной, не NFS, файловой системе.
- Поставлять node collector как проверенный на Python 3.8 `zipapp`/`.pyz` с version/checksum. Systemd вызывает абсолютный путь проверенного Python 3.8, а не `/usr/bin/env python3`; установка не требует `pip` или сети, предыдущий артефакт сохраняется для rollback.
- Формировать manifest последним после atomic rename файлов. SHA-256 обнаруживает порчу; после приёмки центральный контур создаёт отдельный HMAC/signed receipt с проверенными host key и transport record, а ключ хранит вне bundle. Receipt доказывает неизменность после приёмки, но не истинность данных на скомпрометированном узле. Raw store защищается штатным encryption-at-rest, ACL, аудитом и retention.
- Строго проверять имена/пути/размеры bundle members и не использовать небезопасный `tarfile.extractall`. Log excerpts экранировать в Markdown/HTML, чтобы содержимое Pod log не могло внедрить разметку, ссылку или закрыть code fence.

Код/config остаются root-owned и неизменяемыми для service user; единственная writable data area — bounded spool/control state. - Для journald вести отдельный cursor для каждого точного source/query вместе с machine-id, boot ID и последним realtime. Первый старт начинает с утверждённого bounded window; restart использует feature-detected `--after-cursor`. При invalid/vacuumed cursor или смене machine-id выполнять bounded replay с временным overlap, дедуплицировать по `__CURSOR` и создавать `journal_gap`; отсутствие новых строк не считать доказательством валидности cursor.
- Для CRI logs реализовать version-specific adapter с device/inode/offset, обработкой rename/copytruncate, `P/F` fragments, symlinks только внутри разрешённого `/var/log/pods` и namespace/source allowlist. Приоритет: host/control plane/`kube-system`; прикладные namespace — opt-in.
- Писать recoverable `.open`, отбрасывать неполную последнюю JSONL-запись после crash, затем сжимать в `.tmp.gz`, выполнять flush/fsync, проверять hash/manifest, atomic rename в `.ready.gz` и fsync каталога. Для пилота закрывать сегмент не реже 60 секунд либо при 8 MiB до сжатия и выполнять pull примерно раз в 60 секунд; значения пересчитать по нагрузке. Cursor продвигается только после durable append/ready-state; crash до commit даёт безопасный повтор и дедупликацию. При старте agent reconciles `.open/.ready` со `state.db`.
- Ввести hard quota по bytes/age и reserved free space. При overflow сначала удалять подтверждённые сегменты, затем применять утверждённую priority policy. Монотонный durable drop-counter/control record хранится вне удаляемой data queue в зарезервированной control area и обновляется до потери неподтверждённых данных; spool не должен доводить узел до DiskPressure.
- Для первого production-варианта выбрать micro-batch pull закрытых сегментов через OpenSSH по `transport.json` вместо самописного HTTP-сервера. `node_id` задаётся утверждённым inventory mapping и проверенным SSH host key, а не manifest или общей client identity; remote names/segment IDs проходят строгую path-проверку. Ingest ограничивает compressed/uncompressed size, record count/length, копирует в `.part`, проверяет hash, атомарно сохраняет raw, выполняет idempotent commit и только затем подтверждает сегмент.
- Обеспечить `at-least-once`: повторный fetch/ack безопасен, дубликаты подавляются по `segment_id/hash`, центральный outage не останавливает bounded node spool. Если измеренная задержка/стоимость SSH pull не соответствует SLO, новый транспорт/backend проектируется отдельным решением, а не скрыто добавляется в этот MVP.
- Хранить health вне кластера: heartbeat, last cursor, backlog bytes/age, drops, free space и ingest latency доступны через CLI/файл состояния. Prometheus может дополнительно scrape эти данные, но не является единственным мониторингом collector.

[ ] Реализовать внешний Kubernetes LIST/WATCH, центральный ingest и корреляцию потоков.

- Реализовать transport, выбранный feasibility-spike этапа 0. Для `kubectl get --raw` использовать raw watch endpoint; `--output-watch-events` относится к отдельному `kubectl get --watch` механизму и не смешивается с ним. Если выбран `urllib`, поддержать только фиксированные endpoint и явные `server/CA/token-file` либо client certificate settings с hostname verification и без ambient proxy; полный kubeconfig/YAML parser не писать.
- Запустить watcher как systemd service на внешнем центральном узле, не как Pod. Отслеживать Nodes, Pods, Events, Leases, Services, EndpointSlices и основные workloads; права на `pods/log` выдавать только утверждённым namespace, права `secrets/exec/portforward/write` не выдавать.
- Выполнять consistent paginated `LIST`, считать `resourceVersion` непрозрачной строкой, затем запускать `WATCH`. После disconnect использовать bounded exponential backoff с jitter; после `410 Gone` выполнять новый LIST/reconciliation и создавать `watch_gap`, не заявляя восстановление утраченной истории.
- Перед записью watcher проецирует каждый wire object на детерминированный field allowlist; полный Pod/другой объект и необработанный stdout/debug log не сохраняются. Для forensic full-object нужен отдельный чувствительный профиль вне этого плана.
- Принять семантику `at-least-once`: для `ADDED/MODIFIED/DELETED` idempotency key включает cluster, GVK, UID, resourceVersion и event type; `BOOKMARK` и `ERROR` обрабатываются отдельно. При filesystem payload + SQLite общей транзакции нет: payload durable сохраняется раньше cursor, crash может дать повтор, который удаляется дедупликацией. Duplicate, out-of-order, malformed и oversize events не останавливают поток.
- Коррелировать Kubernetes events с journal/pod-log fingerprints, boot/config/package timeline и peer contrast. Одинаковый набор evidence и rule versions должен давать одинаковый replay.
- Добавить малый независимый от Prometheus sentinel-профиль узлов для disk/inode, PSI, memory/PID pressure, conntrack, time sync и spool health с частотой из sizing. Это не замена Prometheus, а минимальная история на случай его отказа.
- Отказ API не останавливает node streams; отказ Prometheus не меняет статус collectors/rules. WATCH использует ограниченный `timeoutSeconds`, периодически перечитывает credential files и явно сообщает об expiry/rotation failure, RBAC denial, gaps и потере данных.
