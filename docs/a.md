## Что такое `/etc/kubernetes/deckhouse/extra-files/authentication-config.yaml`?

### Назначение файла

С помощью модуля `control-plane-manager`, Deckhouse автоматически конфигурирует `kube-apiserver`, добавляя необходимые флаги — в частности, для работы модулей `dashboard` и `kubeconfig-generator`.

Файл `authentication-config.yaml` — это **Structured Authentication Configuration** (структурированная конфигурация аутентификации), появившаяся в Kubernetes 1.27+. Deckhouse передаёт его в `kube-apiserver` через флаг `--authentication-config=`. Модуль CPM автоматически создаёт необходимые конфиги и манифесты компонентов control plane. Именно этот модуль генерирует и кладёт файл в директорию `/etc/kubernetes/deckhouse/extra-files/`.

API сервер требует дополнительной конфигурации для использования аутентификации через dashboard и kubectl. Модуль `control-plane-manager` (включён по умолчанию) автоматизирует этот процесс.

---

### Почему появляется сообщение "файл не найден"?

Это классическая **гонка условий (race condition)** при старте или перезапуске `kube-apiserver`. Вот типичный сценарий:

1. **Deckhouse обновляет конфигурацию** (например, при рестарте пода, обновлении модуля `user-authn`, ротации сертификатов и т.д.)
2. **`kube-apiserver` перезапускается** (как Static Pod через kubelet)
3. В момент старта `kube-apiserver` пытается прочитать `authentication-config.yaml`...
4. ...но `control-plane-manager` **ещё не успел положить файл** на ноду (или файл ещё не смонтирован в Pod)
5. В логах появляется сообщение об отсутствии файла

Изменение feature gates или конфигурации вызывает перезапуск соответствующего компонента (например, `kube-apiserver`). Именно в этот момент и может возникнуть кратковременное отсутствие файла.

---

### Это ошибка или нет?

**Зависит от контекста:**

| Ситуация | Оценка |
|---|---|
| Сообщение появилось **однократно** во время рестарта/обновления, и сейчас файл есть | ⚠️ **Предупреждение, не критично** |
| `kube-apiserver` после этого **успешно запустился** и работает | ✅ **Не ошибка** |
| Сообщение появляется **постоянно** и `kube-apiserver` не стартует | 🔴 **Критическая ошибка** |
| Аутентификация через OIDC/Dex **не работает** | 🔴 **Требует расследования** |

---

### Что проверить

1. **Состояние kube-apiserver сейчас:**
   ```bash
   kubectl get pods -n kube-system | grep apiserver
   ```

2. **Файл существует и смонтирован в под:**
   ```bash
   ls -la /etc/kubernetes/deckhouse/extra-files/authentication-config.yaml
   ```

3. **Свежие логи — нет ли повторяющейся ошибки:**
   ```bash
   d8 k logs -n kube-system kube-apiserver-<node> --tail=100 | grep authentication-config
   ```

4. **Статус модуля user-authn:**
   ```bash
   d8 k get moduleconfig user-authn
   ```

---

### Вывод

Если `kube-apiserver` сейчас работает нормально и файл присутствует на диске — **это не ошибка**. Это нормальное поведение при перезапуске: Deckhouse через `control-plane-manager` сначала рестартует apiserver, а файл появляется чуть позже (или был удалён/пересоздан в процессе обновления конфигурации). Beспокоиться стоит только если сообщения появляются **регулярно** или сопровождаются реальными проблемами с аутентификацией.

Начиная с kdiag 0.9.2 одиночная такая запись не выводится в операторский отчёт. Исторические повторные записи также скрываются, когда файл сейчас существует и читается, `readyz` успешен, а все собранные Pod `kube-apiserver` готовы. Предупреждение остаётся только если одновременно подтвердить эти три условия не удалось. Содержимое файла и видимость файла внутри mount namespace контейнера не читаются и не предполагаются.
